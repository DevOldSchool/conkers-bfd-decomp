# RZIP and asset extraction

RZIP is a storage envelope, not an asset type. A compressed texture, model, or
other resource is still an asset after its four-byte length header and raw
deflate stream are removed.

Use the indexed layout rather than searching the ROM for deflate signatures:

```text
ROM
├── game archive
│   ├── XOR-encoded code-chunk offset table
│   ├── 4 KiB RZIP code chunks → game/code.bin
│   ├── code padding
│   ├── one RZIP data chunk     → game/data.bin
│   └── data padding
├── flat RZIP stream
│   └── sequential compressed entries → assets/flat/
└── asset index
    ├── bank 00 index
    │   ├── compressed entry    → decoded .bin
    │   └── uncompressed entry  → copied .bin
    ├── bank 01 index
    └── …
```

All three researched profiles place one contiguous stream of length-prefixed
RZIP chunks before the two-level indexed banks. Retail US contains 7,760 flat
entries, the renamed debug beta contains 7,808, and ECTS contains 8,427. ECTS
uses a related but distinct raw game-code/data layout. The extractor records
flat and indexed entries separately; neither location determines the decoded
payload's semantic asset type. Retail US has 15 zero alignment bytes between
the last flat chunk and its asset table; debug has three. Those bytes are not
assets and are excluded by the reviewed stream boundaries.

The first game-archive word identifies the compressed data section. The
XOR-encoded table following it identifies every compressed code chunk; its last
offset is the end of compressed code. Code/data padding is therefore separated
exactly rather than treated as an asset.

The later ROM asset table contains eight-byte `(relative offset, size/flags)`
records for each bank. Each bank begins with another eight-byte table whose
flags say whether an entry is compressed. This second index is the source of
truth for individual asset boundaries. RZIP entries are decompressed; raw
entries are copied unchanged. Payload-format identification is deliberately a
later step because a `.bin` may be a model, texture, audio stream, text table,
or another nested container.

Extract the active US ROM:

```sh
./conker rzip-extract
```

Extract either supported debug dump, including byte-swapped `.v64` input:

```sh
./conker rzip-extract \
  --profile debug
```

Extract the ECTS raw game and both asset collections:

```sh
./conker rzip-extract --profile ects
```

Output defaults to `build/rzip/<profile>/` and includes `manifest.json`,
decompressed game code/data, sequential entries below `assets/flat/`, and one
decoded `.bin` per indexed asset. Useful options are:

- `--manifest-only` validates and inventories every entry without writing the
  decoded payloads.
- `--keep-rzip` additionally preserves the raw compressed entries beside their
  decoded forms.
- `--output <dir>` selects a different generated directory.
- `--force` replaces that exact output directory on a repeat run.

The manifest records ROM coordinates, compression flags, decoded lengths,
decoded SHA-1 fingerprints, and output paths so later asset-type tools never
need to rediscover boundaries. Fingerprints are also generated by
`--manifest-only`, allowing cross-version correlation without retaining the
decoded files. The first ROM-derived survey is recorded in the
[asset inventory evidence](evidence/assets/models/us_asset_inventory.md).

## Initial format survey

The boundary inventory is deliberately separate from semantic decoding. The
indexed table's high flag nibble currently proves compression/storage behavior;
it does not by itself prove that a bank contains textures, models, animation,
audio, or text. A safe asset workflow is therefore:

1. preserve the ROM-derived flat and indexed coordinates in the manifest;
2. fingerprint decoded entries and correlate them across US and the betas;
3. prove a payload format from loader code and repeated file structure;
4. add a format-specific extractor and byte-identical verifier;
5. only then give entries stable semantic names and include them in the build.

Related-project examples are recorded in the
[original survey](evidence/assets/models/us_asset_inventory.md#reference-project-lessons);
they do not establish Conker payload formats.

The grayscale font format is independently reproducible outside these two
asset collections: retail US stores 95 small RLE grayscale font glyphs at ROM
`0x40F10:0x42443`, followed by 13 alignment bytes before the game archive.
Each record has width and height bytes, a big-endian total record size at
`+0x4`, and `(intensity, run length)` nibbles whose runs exactly fill the glyph.
The format and its mapping are documented in the
[font evidence](evidence/assets/interface/us_font_atlas.md).

### Font extraction and verification

Fonts have a byte-identical extraction workflow for all three profiles:

```sh
./conker font-assets verify --profile us
./conker font-assets extract --profile us
```

`extract` writes one portable grayscale PGM file per glyph plus a sanitized
manifest. `verify` performs the decode/encode round trip directly against the
normalized ROM. The encoder preserves scanline boundaries and the original
maximum 16-pixel run contract.

### Cross-version correlation

Generate manifests in a temporary directory and correlate their decoded
fingerprints without retaining any payloads:

```sh
./conker asset-correlate
```

The default report is `build/assets/correlation.json`. It uses retail US as the
base and compares both betas. Each shared hash retains every locator in every
profile, so repeated payloads are represented explicitly rather than collapsed
or paired arbitrarily. The summary distinguishes identical locators from
relocated content. Use `--base`, repeated `--compare`, `--output`, and `--force`
for narrower generated reports.

### Editable build inputs

The current extraction convention stores editable glyphs in `build/fonts/us` and
encoded MP3 inputs in `build/assets/mp3-bank/us`. These are not disposable caches
once edited: deleting `build/` or running `make clean` removes those edits. Keep a
private backup outside `build/` before cleaning. A later build initializes absent
input trees from the original ROM; it cannot recover edits that were deleted.
Existing partial trees are rejected rather than overwritten.

Asset part generation follows these real inputs and preserves unchanged output
timestamps. An unchanged asset build does not repack or relink its objects. The
full `raw-build` still runs verification and existing unrelated forced refreshes.
Bank 17 only has reviewed splits and validation; its inputs remain copied ROM
bytes, unlike the rebuilt glyph records and the packed bank-16 MP3 container.

### Loader-proven US MP3 streams and tables

Bank `0x16` is also a reconstructed ROM build input. See the
[MP3 bank build workflow and evidence](evidence/data-layout/us_mp3_bank_build.md)
for its editable stream bundle and preserved index/gaps. MP3 storage is excluded
from the published objdiff report.

The exact US caller loads a selected entry from bank `0x16`, receives both its
ROM address and byte length, and passes those values to `mp3_play_file`. All 453
nonempty entries start with MPEG frame sync and are emitted as sparse-indexed
`.mp3` files. `mp3_play_file` separately calls the indexed loader with paths
`(0x17, 4)`, `(0x17, 5)`, and `(0x17, 6)`; its named destinations and decoder
consumers establish these support roles:

| Bank entry | Role | Size | Storage |
| --- | --- | ---: | --- |
| `0x17:4` | 36-entry Huffman-offset table | `0x90` | raw |
| `0x17:5` | two MP3 lookup tables | `0x4400` | raw |
| `0x17:6` | MP3 Huffman data | `0xA410` | raw |

`mp3dec_init` relocates offset-table slots 1 through 33 against entry 6, while
the assembly utility accesses entry 5 as two `0x2200`-byte halves. The asset
tool validates those invariants and preserves the offset list as JSON.
Entry 6 also retains type flag `0x80`; "raw" only means the RZIP bit `0x10` is
clear:

```sh
./conker mp3-assets verify
./conker mp3-assets extract
```

Extraction writes `streams/<index>.mp3`, preserving gaps in the original
0-through-461 index range, plus the decoder files and a manifest. Verification
rebuilds and checks the 453 stream payloads and three support payloads against
their recorded sizes and SHA-1 values. This classification is
US-only; beta profiles are not assumed to retain the same bank or entry IDs.
Bank `0x17` entries 0–3 are separately proven sound-bank control, external
sound data, wavetable and compact-sequence assets; see
[non-MP3 audio contracts and commands](evidence/assets/audio/us_non_mp3_audio_assets.md).

### Loader-proven US 64x64 CI4 textures

The flat archive has its own code-derived consumer path. `func_15003570` walks
the RZIP stream from ROM `0x1A37E0` and builds the compressed-offset and decoded-
size tables. `func_1510D0EC` resolves a flat index, decompresses that entry, and
caches it in `D_800B0E58`; the custom display-list parser `func_1510BF60`
resolves its texture opcode (`-3`, byte `0xFD`) against that same cache.

A bounded family of 704 decoded entries is exactly 2,080 bytes:

| Component | Encoding | Bytes |
| --- | --- | ---: |
| pixels | 64x64 CI4, high nibble first | 2,048 |
| palette | 16 big-endian RGBA5551 colors | 32 |

Most payloads store odd scanlines in TMEM-ready order: within each eight-byte
group, the two 32-bit halves are exchanged. Leaving those bytes untouched makes
the PNG look horizontally interleaved even though it still round-trips. The
extractor reverses that permutation for ordinary PNG scanlines and round-trip
verification reapplies it. Flat indices `1296` and `1297` use linear scanline
order; their
64-pixel sprite call sites and coherent source order make them explicit
manifest exceptions instead of relying on an image-content heuristic.

The source scanlines use a bottom-left image origin. This is visible in
directional artwork, including the legible `MILK` and `SAFE` lettering in flat
index `1063`. Extraction reverses the row order for PNG's top-left origin;
round-trip verification reverses it again before applying the stored row
layout.

The tool writes all entries as 64x64 four-bit indexed PNGs, retaining all
palette slots, transparent RGB values, and original pixel indices:

```sh
./conker texture-assets verify
./conker texture-assets extract
```

Manifest schema 3 records each entry's row layout and the source/PNG origins.
Verification round-trips all 704 entries byte-identically.

### Runtime-proven rectangular CI4 textures

The 1,056-byte decoded-size group is not one uniform texture family. Each
compatible payload can hold 1,024 bytes of CI4 pixels and a 32-byte palette,
but the runtime selects both 64x32 and 32x64 dimensions. Some other members use
more complex tile/load sequences and cannot be classified from size or visual
appearance alone.

`texture-assets survey` scans decoded indexed-bank display lists for the exact
loader contract: a direct flat-index texture reference, a trailing-palette
reference (`payload_end - 0x20`), and a CI4 tile line value that proves the
width. On the verified US ROM, 13 of 1,840 size candidates meet that complete
contract with no conflicting dimensions. Another 12 direct references use an
8-bit render path with a 256-entry TLUT and are explicitly excluded from this
16-color family.

The survey also validates the exact `func_15000AD0` code signature, its
`func_1510D0EC` call, the 360-entry loop bound, and the seven pointers at
`0x800891BC`. The preload ranges contain 1,573 unique 1,056-byte candidates.

The corresponding consumer is now bounded as well. `func_15111AF4` selects
five view bases from each pointer-table record and passes each selected base to
`func_15110CFC`. That renderer walks a 360x360 view as six columns by twelve
rows of 60x30 visible tiles, using column-major flat indices. Its verified
format tables select either a 2,560-byte CI8 tile or a 1,056-byte CI4 tile. The
CI4 path uses 64x32 storage, 1,024 bytes of pixels, a palette at `+0x400`, and a
16-entry TLUT. The ordinary grids prove 1,816 of the size candidates as runtime
CI4 tiles. A separately guarded branch in `func_15110CFC` conditionally
substitutes the six-entry range `5747:5753`; four members are CI4 and two are
CI8. This raises the runtime-proven CI4 count to 1,820. None remain
preload-only, and only five candidates now lack a recovered runtime reference.
Eight CI4 tiles also have a separate direct 256-entry-TLUT use, so the survey
records that dual-use overlap rather than treating the classes as mutually
exclusive.

The tiled-view extractor emits all 35 logical 360x360 views as RGBA previews.
It applies the renderer's two-entry phase to the continuous column-major stream:
the first two visible tiles come from indices `base - 2` and `base - 1`, then
indices `base` through `base + 69` follow. This produces source row order 10,
11, then 0 through 9 without incorrectly wrapping rows 10 and 11 inside each
column. That distinction moves the upper pieces of structures into the next
column and carries the final pair across a view boundary. Each 64x32 storage
tile is cropped to its 60x30 visible area.

Because each view mixes per-tile palettes, the extractor also emits indexed
CI4/CI8 tile PNGs beneath `tiles/`. The manifest retains the union of 2,526
runtime-selected records and 2,520 preview-used records: 2,534 unique payloads,
including eight context-only records and fourteen runtime tail records. The
five 1,536-byte 32x32 CI8 records are among those runtime tails and are not used
in the assembled previews. Round-trip verification rebuilds all 2,534 retained
payloads byte-identically.

```sh
./conker texture-assets survey
./conker texture-assets verify --family 1056-proven
./conker texture-assets extract --family 1056-proven
./conker texture-assets verify --family tiled-views
./conker texture-assets extract --family tiled-views
```

Survey schema 4 records positive contracts, direct incompatibility evidence,
the validated preload ranges, and the tiled-renderer contract. Standalone
extraction schema 4 records width and height per promoted texture plus the
display-list locations that proved them. Tiled-view schema 5 records view
assembly, tile format, placement, and reversible source file. The same
bottom-left to top-left conversion and reversible TMEM odd-row conversion used
by the 64x64 family apply here.

Editing and ROM insertion are intentionally outside the current decompilation
workflow. Their future-facing commands and constraints are documented in
[Future asset editing and recomp integration](asset-editing.md).

### Direct CI8 storage contracts

`texture-assets survey --family ci8-proven` scans decoded indexed-bank display
lists for local CI8 render tiles. Promotion requires agreement between the
render-tile stride, explicit tile bounds, 16-bit load length, decoded payload
size, same-index mode-one palette reference and 256-entry TLUT. It accepts
only zero-DXT full loads of at most 2,048 pixel bytes. Missing or contradictory
contracts remain in the generated survey rather than becoming textures.

The palette reference `0x00400000 | flat_index` is verified against
`func_1510CE60`. Mode bit 0 selects decoded payload end minus `0x200`,
independently of the fifth argument. At `0x1510CFBC`, `$t9` is overwritten
with `mode & 1` before the branch; the earlier fifth-argument value is no
longer live. The bookkeeping pointer does not select the palette. The local
command contract proves a same-index 256-entry TLUT, while final runtime
appearance still requires the selected draw state. Index 3358 is included
again because its cache-store observation preceded palette relocation.
The manifest retains all 256 RGBA5551 words and dimensions per texture.

```sh
./conker texture-assets survey --family ci8-proven
./conker texture-assets extract --family ci8-proven
./conker texture-assets verify --family ci8-proven
```

The reviewed set contains 528 textures and 1,246,752 decoded bytes. PNG
round-trip verification is a storage guarantee, not complete visual validation;
the earlier full-ROM no-op pack covered the 527-entry set. Previews default to
TMEM-ready odd rows and bottom-left source origin. Fifty-six reviewed payloads
use a reversible transposition of the render-tile bounds; index 2376 instead
uses a reviewed 16x128 geometry. These overrides preserve decoded bytes and are
not inferred automatically from image content.

The 32x32 examples 2795 and 4423 and the 32x64 interpretation of 3560 remain
visually unresolved. `visual_validation`, `row_layout_evidence`,
`preview_geometry_evidence`, and `preview_status` retain those boundaries.
The survey's [CI8 extraction evidence](evidence/assets/models/us_asset_inventory.md#direct-ci8-extraction-and-verification-boundary)
records the reviewed layouts. The
[palette relocation correction](evidence/assets/materials/us_model_palette_relocation.md)
explains why the cache-store watchpoint on index 3358 proves only its payload
base: relocation happens later, and a null fifth argument does not suppress it.

### Direct RGBA16 storage contracts

`texture-assets survey --family rgba16-proven` recognizes a plain flat-index
`FD100000` texture-image reference only when the following local commands
also prove an RGBA16 render tile, explicit bounds, matching line stride, a full
zero-DXT load, and a decoded payload whose size is exactly
`width * height * 2`. Palette uploads, partial loads, reused state, and
contradictory consumers are not promoted.

```sh
./conker texture-assets survey --family rgba16-proven
./conker texture-assets extract --family rgba16-proven
./conker texture-assets verify --family rgba16-proven
```

Six flat entries satisfy the complete contract: 53, 322, 834, 3286, 3291, and
3292. Their dimensions are 64x32, 32x32, 32x16, and three further 64x32
textures, respectively, totaling 19,456 decoded bytes. Extraction writes
truecolor RGBA PNGs, preserving every RGBA5551 color including RGB channels on
transparent pixels. Packing and verification reverse the bottom-left origin
and odd-row TMEM ordering byte-identically.

This family has no separate palette or palette relocation. Its local commands prove the storage and rendering
format, not semantic names or that each isolated preview should look like
finished artwork.

### Other direct native-color contracts

The `native-proven` family applies the same full-payload rule to formats that
do not use a separate palette:

```sh
./conker texture-assets survey --family native-proven
./conker texture-assets extract --family native-proven
./conker texture-assets verify --family native-proven
```

The survey promotes 91 entries: 40 RGBA32, 14 IA8, four IA16, 14 I4, and 19
I8. Every record has a format-matching image command and render tile, explicit
bounds, matching line stride, a full zero-DXT load, and a decoded payload of
exactly the required pixel size. The family covers 322,048 decoded bytes.

Extraction uses truecolor RGBA PNGs for all five formats. IA and intensity
encoders reject channel values that cannot reproduce the original packed bits;
RGBA32 retains all four bytes directly. The TMEM conversion is format-aware:
RGBA32 odd rows exchange eight-byte halves within each 16-byte group, while the
narrower formats exchange four-byte halves within each eight-byte group. The
TMEM and image-origin conversions are reversed during verification. A no-edit
pack of all 91 entries reproduces the complete US ROM SHA-1.

No IA4 reference currently has a complete full-payload contract. Partial loads,
payloads with unexplained trailing data, and conflicting local consumers remain
survey evidence and are not promoted based on appearance.

### Character containers and animation

`func_1503CF20` proves bank-01's 56-byte headers and seven offset/size regions:
vertices, primary and alternate display-list tables, joints, texture descriptors,
normal data and procedural animation indices. `func_1503DC3C` initializes each
12-byte texture descriptor's pointer slot from its flat index and retains its
width and height. Character lists use an RGBA16 transfer image with a 4-bit or
8-bit RGBA render tile and a same-index mode-two or mode-one TLUT; this proves
effective CI4/CI8 sampling, not RGBA sampling.

`func_150A81D0` establishes 16-byte joints and 64-byte runtime matrices. Stored
translations are parent-relative. The exporter accumulates bind pivots, bakes
joint-local vertices through them and emits inverse-bind translations.
`DA380003` selects matrix slots; cached vertices retain the matrix used when
loaded. glTF receives the rigid skin and a paired animation-free `*-bind.gltf`
for geometry inspection. See [vertex-load ownership](evidence/assets/models/us_character_vertex_load_matrices.md)
and the [container and animation proof](evidence/assets/models/us_asset_inventory.md#rigged-character-model-geometry-and-animation-companions).

Bank-02 companions retain paired descriptor/stream boundaries and direct
payloads. The fixed source-frame stride is descriptor byte 5, consumed by
`func_1502D824` after `func_1505E0C4` copies into zeroed runtime state.
`func_150A8A18` decodes optional masked translations, root motion, rotations and
scale. Per-frame tails, alignment, empty streams and post-duration companion
bytes remain preserved rather than being interpreted as extra frames.
Entry `0082`, pair `0000`, needs two zero descriptor bytes supplied by the
runtime's zeroed destination and retains six tail bytes per frame. Entry `0083`,
pair `0018`, retains two tail bytes per frame; neither layout is guessed.

Rotations are signed full Euler angles; glTF transposes the row-vector runtime
matrix convention and uses quaternion half-angles. Root translation uses
`1/1024`; masked signed joint translations use `1/16` before parent composition.
Rotation bit `0x10` introduces a scale descriptor. Missing/zero scale is unity;
other scale values are unsigned values divided by `16384`. Unreferenced channels
remain in the manifest. Descriptor-relative timing includes shortened final
intervals and the proven 30 Hz clock. Bank-15 routes map logical animation IDs
to bank-02 pairs; character duration overrides come from `D_800993F8`.
The evidence above retains duration exceptions, route counts and trace results.

The sixth header pair is the alternate list table selected by `func_1502CCFC`.
The final pair supplies procedural joint indices to `func_1503DA3C` and
`func_15034860`, with `0xFF` as the absent sentinel. The fifth pair is the
`DC38000E` normal stream relocated by `func_1503D368`/`func_1503D438`.
Conker's CBFD microcode uses signed X/Y at `base + cache_slot * 2` and signed Z
from the low vertex-flag byte. This is not the standard F3DEX2 MoveMem matrix
meaning. glTF normalizes nonzero source normals and explicitly records geometric
preview fallbacks for zero or unavailable corners; bank-03/04 share this rule.

### Direct models, bundles and collision

Bank-04 has contiguous, eight-byte-aligned `(offset, size)` pairs. The first
offset equals the table size, zero-length entries retain their positions, and
only the last size has bit 31 set. Applying the loader's `0x0fffffff` size mask
makes the last range end at the decoded file boundary. The loader relocates
nonempty `[04, entry]` segments into model records. In their 40-byte headers,
bytes from `+0x28` to the primary display list are 16-byte vertices. The parser
supports ordinary triangles and Conker's packed four-triangle opcodes `0x10–0x1f`.

OBJ geometry preserves signed source positions. UVs apply `D7` scale, `F5` tile
shift and `F2` bounds (or masks if bounds are absent), then convert image origin.
Secondary and tertiary regions remain separately preserved. The first model's
tertiary region skips an eight-byte header and supplies one four-byte surface
word per primary collision face; its second header word is `5`.
`func_15003668`, `func_15001460` and `func_15002754` build collision records and
bounds. `model-assets collision` writes the surface words byte-identically and
represents each runtime vertex-pointer triple as three big-endian model-relative
offsets. Model slot 3 supplies another static collision layer without an installed
surface table. Zero-area source records remain in the binary inventory.

Placement collision follows source byte `0x32`, copied to runtime `+0x4F`, and
excludes exactly `(flags & 0x60) == 0x20`. Missing bank-04 bundles in scenes 17
and 62 remain unresolved. Surface semantics, later-slot tertiary regions and
secondary-region meanings require separate evidence. See
[bank-04 format and collision evidence](evidence/assets/models/us_asset_inventory.md#indexed-bank-04-model-geometry)
and the [scene consumer graph](evidence/assets/models/us_model_scene_consumers.md).

Five models contain sentinel-terminated 12-byte vertex-colour descriptors.
The loader rebases their first two pointers; `func_151739B0` reads RGB triples
and `u16` vertex indices. Header word 9 has bit 31 set and otherwise stores the
complete descriptor-table size, including the sentinel, or zero when word 8 is
zero. The [vertex-colour target evidence](evidence/assets/materials/us_scene_vertex_color_targets.md)
records the source tables, bounded integer interpolation and conditional links.

Bank-03 uses the same direct 40-byte model header. Object setup proves two
`0x44`-byte placement sources: `[0B, scene]` dispatched records and `[0C, scene, 2]`
direct records. Position is at `+0x00`, Euler degrees at `+0x06`, the direct model
index at `+0x10`, and scale at `+0x20`. `func_1511490C`, `func_151148A8` and
`func_150A8050` prove YZX rotation and the matrix convention. See
[direct-model and placement evidence](evidence/assets/models/us_asset_inventory.md#direct-object-model-geometry-and-placement-records).

Bank-09 includes direct models, [relative-address models](evidence/assets/models/us_bank09_relative_models.md),
attachments and [effect containers](evidence/assets/models/us_bank09_effect_models.md).
`func_1502FE10` proves the attachment layout: three offset/size pairs, vertices
at `+0x18`, a callable part-pointer table, optional 16-byte joints and a CBFD
normal region. Parsed fields and retained native regions reconstruct exactly;
the [initial subset evidence](evidence/assets/models/us_asset_inventory.md#initial-bank-09-direct-model-subset)
is historical, not the current inventory.

### Materials and preview boundaries

`func_1510CE60` recognizes `FD`, separates mode bits, resolves the low 22-bit
flat index through `func_1510D0EC`, and relocates the command. Segmented
references remain dynamic. `F3` commits pixel data, `F0` commits palette data,
`D7` bit 1 enables texturing, `FC` supplies the combiner, and `EF` or a segment-8
call supplies OtherMode. Ordered OBJ groups/material names retain the exact
image command, index or segment address, mode and palette binding. MTL does not
invent texture paths for unproven images.

Preview consumes the six proven texture catalogs and verifies generated files
and relative dependencies. Mode-one CI8 palettes use the trailing `0x200` bytes;
mode-two CI4 palettes use the trailing `0x20`, independently of the bookkeeping
argument. glTF includes source vertex RGBA and material-local UVs; OBJ/MTL cannot
represent the vertex-colour combiner and is less suitable for material review.
See [model appearance extraction](model-appearance.md) for ROM-only inputs,
guarded consumer fallbacks, explicit presets and coverage interpretation.

Character segments `6`, `7`, `10` and `11` are state slots: `func_150911F4`
loads four `u16` IDs from `D_800D24C8 + 0xB0..0xB6`. Primitive/environment RGB
comes through `func_1502CC34` from `D_800D9B68`/`D_800D9B78`, caller alpha and
`func_1502EC34` effects. `func_1502CCFC` emits `FA00F200` and `FB000000` before
the character lists. These dependencies do not justify a single guessed PNG
or colour. Renderer-provided segment-8 lists contain `EF` plus `DF`: they change
render state rather than adding geometry, and nested calls must replay segment
changes in command order.

For an exhaustive manifest-driven Blender import check:

```sh
blender --background --factory-startup --python \
  scripts/validate_model_previews_blender.py -- --model-root build/assets/models
```

`model-assets materials` converts correlated `mupen-trace` JSONL into a
ROM-hash-checked catalog. `model-assets preview --runtime-materials <manifest>`
retains observed variants and applies only supported, unambiguous translations;
`--runtime-appearance TRACE_INDEX:EVENT_INDEX` selects one captured task.
Missing observations fall back only to independently proven static material.
Runtime `SHADE` replay needs one complete lighting context and is emulator
evidence, not independent hardware proof. Captured mip levels, `SetConvert`,
two-texture formulas and unresolved inherited state remain explicit metadata
where glTF cannot reproduce them.

For capture commands and task-local character composition, use
[runtime tracing](runtime-tracing.md#record-model-draw-state). Historical corpus
outcomes and the entry-0130 pointer-identity resolution remain in the
[inventory evidence](evidence/assets/models/us_asset_inventory.md#indexed-bank-04-model-geometry);

### Flat RZIP reconstruction evidence

The packer validates the original ROM and a supported texture manifest. It
copies every unchanged compressed chunk verbatim and emits a new raw-DEFLATE
RZIP chunk only when a decoded payload changed. An unchanged payload set must
reproduce the complete verified source ROM, including original compressed
bytes and the 15-byte alignment gap. Modified output is validated by decoding
every rebuilt flat entry. Indexed asset-bank insertion remains separate future
work. Operational editing and insertion guidance lives in
[Future asset editing and recomp integration](asset-editing.md).
